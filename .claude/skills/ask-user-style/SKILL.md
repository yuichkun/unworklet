# ask-user-style

余湖さんに報告する時・判断を求める時の規範。順番は「① Artifact を publish → ② TUI に 1 行 intro + link → ③ AskUserQuestion」。

## 1. チャットは読まれない前提で書く

- 余湖さんはチャットを全部は読まない。チャットに経過・途中報告・調べた結果を流さない。
- 伝えることは Artifact に自己完結させる。チャットは 1 行の案内とリンクだけにする。
- 質問するときは、軽い選択でも必ず先に簡潔な Artifact を作る。チャットの過去ログを読んでいないと分からない質問をしない。

## 2. 誰向けかを意識し、判断すべきことだけに絞る

- 読み手は余湖さん(unworklet の作者)。プロダクトの目的、Web Audio、コードベースの基本は知っている。それらを説明し直さない。
- 載せるのは「余湖さんが判断するために要ること」だけ。調べたこと全部、関連する話題全部を並べない。判断に関係しない状況報告・一覧・経緯は削る。
- 冒頭に「何を決めてほしいか」と推奨を書く。根拠は、読み手が判断に必要な順に短く並べる。

## 3. まず「消せないか・シンプルにできないか」から考える

- 何か(コード・テスト・docs・仕様・ツール・作業)を提案する前に、消す・簡素にすることで目的を果たせないかを検討する。足す提案は、それで済まないと確かめてから出す。
- 作業がそもそも目的から外れていないかを、設計時の意図(`docs/decisions-log.md` など)と照らして確かめる。外れている作業は、完璧にする方向ではなく、捨てる候補として出す。

## 4. Artifact の書き方

- 冒頭: 決めてほしいことと推奨。
- 本文: 判断に要る根拠だけ。PR・issue・文書を参照するなら、判断に要る範囲で中身を見せる(何のもので、どこにあり、何と書いてあるか。英語の原文なら訳も)。番号や「ガイドの記載」のような呼び名だけで済ませない。
- コードは最小限にし、載せるなら必ずシンタックスハイライトを付ける(例: cdnjs の highlight.js を版数固定で読み込み、配色はライト・ダーク両テーマのトークンで定義する)。
- 各案: 何をするか、良い点・悪い点、選んだ後に何が起きるか。
- 状況が変わったら(PR がマージされた等)、追記せず作り直し、要らなくなった記述は消す。

## 5. AskUserQuestion

- label は 5-15 字の平易な日本語。略語・記号・参照番号・英語の実装用語を入れない。
- description にその案の中身とメリデメを書く。コードで違いが出る案は `preview` にコードを載せる。
- 推奨は最初の option に置き、label 末尾に `(Recommended)` を付ける。
- 一度に 1 問。互いに独立した「捨てる候補」などは、multiSelect の 1 問にまとめてよい。

## 6. 言葉遣い

- きちんとした、平易で丁寧な日本語で書く。読む人が一瞬でも「これ何?」となる略語・社内コード・未説明の参照番号を残さない。
- 目的は、読む人が迷わず、負担なく判断できること。自分の頭の中の文脈を押し付けない。

## NG

- チャットに経過・途中報告を流す / 余湖さんがチャットを読んでいる前提で書く
- Artifact なしで質問する(軽い選択でも)
- 調べたことを全部並べる / 読み手が知っている基本を説明する / 判断に関係しない一覧や経緯を載せる
- 足す方向の案しか出さない / 目的から外れた作業を、捨てずに直す方向で進める
- 説明より先に選択肢を出す / 説明を TUI の長文やローカルの md で済ませる
- PR・文書を番号や呼び名だけで示す / コードをハイライトなしで載せる
- 古い記述を残したまま追記する
