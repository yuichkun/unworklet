# ask-user-style

余湖さん に 判断 を 求める 時の 規範。 順番 は 毎回 「① Artifact で 説明 を publish → ② TUI に 1 行 intro + Artifact の link → ③ AskUserQuestion」。 説明 を 省いて 選択肢 だけ を 投げない。

## 大前提 1 — 判断を求める前に、きちんと説明する(これを欠いたら、形が整っていても失格)

判断を求める時点で、余湖さんが **判断に必要なことを全部知っている状態** にしておく。余湖さんはこの会話の文脈も、調べた中身も覚えていない前提で書く。

- **前提になるものは、番号や名前だけで済ませず中身をブリーフィングする。** PR・issue・ブランチ・Codex など別の作業者のやりかけ・調査結果・CI の状況など、判断に出てくるものすべてが対象。PR なら最低限これを書く:
  - 何の問題を解決するものか(最小コードで「期待」と「実際」)
  - なぜその問題が起きるのか(平易に)
  - どう変えるのか(仕組みの説明と、主要な差分の抜粋コード)
  - テスト・ガイドの変更
  - 今の状態(CI・レビュー・競合・マージできるか・試していないこと)
  - 自分の見立て(マージしてよいか、など)
- **説明は Artifact で出す。** TUI の長文や、ローカルの md ファイルで済ませない。コード・表・図を並べて読め、後から見返せる形にする。作り方は Artifact tool の手順(quickstart → ページ作成 → publish)に従う。
- **判断に出てくる用語は、Artifact の中で意味を説明する。** 読む人が「これ何?」となる言葉を残さない。

## 大前提 2 — 言葉遣い と 愛

質問の「形」より前に、まず **読む人(余湖さん)への配慮** がある。これが無い伝え方は、他がどれだけ正しくても規範違反。

- **きちんとした、平易で丁寧な日本語で書く。** 即興の略語・内部記号・未説明の参照番号(`#4` `Q46` 等)・英語の実装用語(`witness` `lowerToProcessor` 等)を、説明なしで option に置くな。初めてその文だけを読む人が「何の話か」「これを選ぶと何がどうなるか」を分かる言葉にする。本物の技術用語は使ってよいが、意味不明な造語・社内コード・噛み砕いていない jargon は禁止。
- **option は必ず「中身」を説明する。** label + 一行 jargon で済ますな。各 option は「これを選ぶと具体的に何がどう変わるか」と「メリット / デメリット」を、平易な日本語で書く。「どう直すか」と問うなら、各案が **どう直すのか** を必ず説明しろ。説明のない選択肢を投げるのは、判断を相手に丸投げするのと同じ。
- **可能な限り example code を出す(これは毎回 言われている)。** 問題も、各案がどう直るかも、言葉だけで説明せず **最小の before / after コード** で見せる。コードで示せるものを散文で済ますな。問題は「今こうなる」を 1 ブロック、各案は「この案だとこう書ける / こう変わる」を 1 ブロックずつ。選択肢ごとにコードが違うなら、Artifact に並べたうえで、AskUserQuestion の option の `preview` フィールド(コード比較用)にも各案のコードを載せる。
- **メリデメを整理して並べる。** 良い点・悪い点・コストを、相手が一目で比べられる形にする。trade-off を 1 文に畳むのは、その 1 文が平易で意味が通る時だけ。通らないなら畳まず、ちゃんと説明しろ。
- **「愛」と「優しさ」を持って書く。** コミュニケーションの目的は、相手が **迷わず・負担なく・気持ちよく** 判断できること。自分の頭の中の文脈や略語を相手に押し付けない。相手が一瞬でも「これ何?」「どういう意味?」となる言葉・構造は、書いた時点で失敗。読む人を思いやらない伝え方は、形が整っていても NG。

### 悪い option / 良い option(同じ判断)

❌ 悪い(jargon・中身ナシ・コードも無し。読む人は何を選ぶのか分からない):

- `#4 も直す(推奨)`
- `footgun 全部 library`

✅ 良い(まず問題を最小コードで見せ、各案がコードでどう変わるかを示す):

問題(まずコードで):

```ts
// main から小数を送ると、worklet では整数に丸められてしまう
node.events.ctl.emit({ gain: 0.8 }); // worklet 側: e.gain === 0  ← 0.8 が消える
```

選択肢(label は平易に、各案のコードは AskUserQuestion の `preview` に載せて並べる):

- label `小数がそのまま届くよう直す` — preview:
  ```ts
  node.events.ctl.emit({ gain: 0.8 }); // 直すと: worklet 側 e.gain === 0.8
  ```
  良い点: 宣言どおり 0.8 が届く。悪い点: 送受信の仕組みに手を入れるので作業は大きめ。
- label `直さず、整数で送る書き方を案内` — preview:
  ```ts
  node.events.ctl.emit({ gainPct: 80 }); // worklet 側で /100 して 0.8 を得る
  ```
  良い点: すぐ出せる。悪い点: 使う人が「小数は整数にして送る」回避を覚える必要。

## 規範の手順

1. **Artifact を作って publish する**(構成は次節)。質問 1 つにつき専用のページを作る。既存の調査メモや集約ページを指して済ませない。
2. **TUI = 1 行 intro + Artifact の link だけ。** 説明・list・表・長文は TUI に書かず、すべて Artifact に入れる。
3. **AskUserQuestion で選択肢を並べる。**
   - **label = 5-15 字、平易な短い日本語**(略語・記号・参照番号・英語の実装用語を入れない)
   - **description = その案の中身 + メリデメを平易に。** 「何をする案か」「選ぶと何が良くて何が悪いか」が、その文だけで誰でも分かること。terse に削って jargon だけ残すのは禁止
   - **コードで違いが出る案は、option の `preview` に before/after の最小コードを載せる**
   - recommend は label 末尾 `(Recommended)` か最初の option に置く
4. **一度に 1 問。** 次の質問は前の回答を記録してから。

### Artifact の構成

上から順に、判断に必要なものだけを置く。

1. **要点** — 何の判断か、現状の結論、推奨を数行で
2. **用語** — 判断に出てくる用語を平易に(必要な分だけ)
3. **前提のブリーフィング** — 関係する PR・issue・作業・調査の中身(`大前提 1` の項目)。状況が数字で表せるなら表にする(例: CI の失敗の内訳)
4. **問題** — 最小コード例で「期待」と「実際」を 1 行コメントで
5. **なぜ** — 根本原因を平易に。数字や再現結果で裏付ける
6. **どう直すか(選択肢)** — 案ごとに「何をする案か」「before / after のコード」「良い点・悪い点」「選んだ後に何が起きるか(1 行)」
7. **推奨と、なぜそれを推すか**
8. **決まった後の手順**(必要なら)
9. **調べたもの**(根拠の範囲)

### 内容が複雑なら図で見せる

判断が「1 バグ + 2-3 案」で完結する軽い話なら、上の構成とコード例で十分。だが判断の内容自体が複雑 (複数系統・現在地の把握が要る・分岐先で到達点が違う・時系列・依存関係) な場合は、**言葉だけで済まさず Mermaid 図で視覚的に見せる**。Artifact では `<pre class="mermaid">` がそのまま描画される(`explain-with-diagrams` skill の作法に従う)。

- **全体像 / 分岐 → `flowchart`**: 現在地から各案の到達点までを 1 枚で。「今どこにいて、選ぶとどこに行くか」を 1 スクロールで掴ませる。
- **時系列 / 状態遷移 → `sequenceDiagram` / `stateDiagram-v2`**: main ⇄ worklet の交換、build → tsc → dev の順序、cold → warm の遷移など。
- **概念マップ → `mindmap`**: 案が複数の観点で違うとき、観点ごとの branch。
- **before / after のコード比較**: これはコードで見せる。図と併用可。

判断に効くなら図で表現する。判断に効かない装飾図 (実装内部の module 依存図など) は書かない。図 vs 散文の選択基準は「相手が読む時間を短縮するか」。

Mermaid 使う時の落とし穴:

- label 内の半角 `(` `)` は全角 `（` `）` に置換 (node-shape syntax と衝突して blank になる)
- reserved keyword (`graph` `end` `class` `subgraph` 等) を node id に使わない
- `stateDiagram-v2` は 1 行 1 遷移、`A --> B --> C` の chain は禁止

### Artifact に書かないこと

- 判断に効かない内部実装の細部。ただし、前提のブリーフィングに必要な仕組み・差分の説明は省かない
- 決定後の詳細な実装計画。「選んだ後に何が起きるか」の 1 行は書く
- 自己弁護の長文。メリット / デメリットは各案に簡潔に付ける
- Q番号・spec 引用の羅列
- 判断に効かない装飾図

## 送信前の self-check(AskUserQuestion を叩く前に毎回)

- Artifact を publish し、TUI にその link を貼ったか
- 判断に出てくる PR・issue・ブランチ・作業は、すべて中身を説明したか。番号や名前だけのものが残っていないか
- 問題と各案をコードで見せたか。各案にメリデメと「選んだ後に何が起きるか」を書いたか
- 推奨と理由を書いたか
- この件を初めて聞く人が、Artifact だけを読んで迷わず判断できるか
- option の label・description に、未説明の用語や番号が残っていないか

一つでも欠けていたら、直してから送る。

## Artifact を省いてよい場合

前提知識が要らず、選択肢の説明文だけで完結する軽い選択だけ(例: 作業の順番、名前の候補から選ぶ)。この場合は TUI 1 行 intro + AskUserQuestion でよい。PR・issue・調査結果・コードや設計に触れる判断は、軽く見えても省かない。

## NG form

- 説明より先に選択肢を出す / Artifact を出さずに AskUserQuestion を叩く
- PR や issue を番号・タイトルだけで示し、中身(何の問題を、どう変えるものか、今どういう状態か)を説明しない
- 説明を TUI の長文やローカルの md ファイルで済ませる
- 複数案を TUI 内で list 化してから、同じ内容を AskUserQuestion で再 list
- jargon・略語・内部記号・参照番号を option に置く(説明なしの用語散布 = 読む人が意味を取れない)
- option の中身やメリット / デメリットを説明しない(「どう直すか」と聞いて選択肢を説明しないのは最悪)
- コードで違いが出る案なのに、コードを見せず散文だけで済ます
- 1 turn に複数の質問を詰める(依存する質問は段階的に出す)

## OK 例

```
0.6.0 を出す前に決めてほしいことが 1 つあります。説明: https://claude.ai/artifact/…

[AskUserQuestion]
- テストをガイドに合わせる (Recommended) — 説明 + preview にコード
- そのまま再実行で出す — 説明 + preview にコード
- 根本修正まで止める — 説明 + preview にコード
```

Artifact 側の構成の例(このときに作ったもの): 要点 → 用語 → CI の失敗の内訳(表)→ やりかけ PR 2 本それぞれのブリーフィング(何が起きていたか・なぜ・どう直したか・テスト・今の状態・見立て)→ ほかの PR → リリース前に必要な作業 → 選択肢 3 つ(コード・メリデメ・選んだ後)→ 推奨 → 決まった後の手順 → 調べたもの。

## NG 例

```
結論: main は緑だがブラウザテストが不安定。
Codex 側のやりかけ:
- PR #182: …… このままマージできます。
- PR #181: …… 本体の修正は見つからないまま。
赤になる原因: 1. …… 2. …… 3. ……
決めていただきたいのは 1 点だけです(詳細は /tmp/…/decision.md)。

[AskUserQuestion]
- ...
```

TUI に長い報告を書き、詳細をローカルの md に逃がし、判断の前提になる PR 2 本の中身(何の問題を、どう直すもので、今どういう状態か)を説明しないまま選択を求めている。余湖さんは選ぶ前に自分で PR を読み直す羽目になる。

## なぜ

- 判断の材料が揃っていないと、相手は自分で調べ直すか、よく分からないまま選ぶことになる
- Artifact なら、コード・表・図を並べて読める。TUI の長文やローカルの md より読みやすく、後から見返せる
- jargon 散布 = 各用語を噛み砕く段階を余湖さんに押し付ける
- AskUserQuestion に寄せる = label / description の文字数制約で自動的に短文化 + 判断軸が明確化

## 起動

- 余湖さん に 何か を 選んで もらう / 方向性 を 確認 する 任意の 場面
- 原則: Artifact で説明 → TUI 1 行 intro + link → AskUserQuestion
- 例外: 上の「Artifact を省いてよい場合」だけ、TUI 1 行 intro + AskUserQuestion
- 累犯 entry: `feedback_no-tui-bulk-send.md` / `feedback_no-jargon-sprinkling.md` / `feedback_concise-communication-style.md` と zip
